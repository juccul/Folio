# Development status — Folio 0.1.5

Updated 2026-10-15. Folio is a runnable Rust/GPUI Linux and Windows desktop application. Production certification still requires physical tablets and additional desktop/distribution sessions; synthetic events and CPU benchmarks do not establish hardware-to-display latency.

Version 0.1.5 reduces editor rendering and idle maintenance work, releases stale preview/GPU resources, and speeds up selection and object maintenance. It also corrects false spaces inside compact handwritten numbers and evaluates held arithmetic when checking fractional-power steps. Windows setup/portable and signed Flatpak packages share the same release source. See `WINDOWS.md` for Windows Ink support and validation limits.

## Continuous integration

The `Linux and Windows` workflow tests every branch push, pull request and tag,
and can be started manually with `workflow_dispatch`.
New pushes cancel superseded runs on the same branch,
and pull request updates cancel superseded runs for that pull request. Release
tag builds and manually started builds are not cancelled by branch updates.

Rust tests run with two test threads in CI to limit contention between each
controller's storage and rendering workers. Asynchronous worker behavior remains
covered. To use the same limit locally, run
`cargo test --locked --workspace -- --test-threads=2` on Linux or
`./scripts/build-windows.ps1 -Test -TestThreads 2` on Windows. Omitting
`-TestThreads` preserves Cargo's default parallelism for local Windows builds.
Updater, packaging, math protocol and Rust checks have separate CI steps so the
failing check is visible directly in the run summary.

## Scratch erase — current source

Recognition separates a geometric scrub candidate from the decision to erase. Compact retracing accepts three broad passes with an ink hit; advancing up/down scrubs accept six broad legs and require three legs to cross existing non-highlighter ink. Rounded corners, unequal amplitudes, diagonal travel and slow gestures are supported. Both footprint/travel axes and their perpendiculars are inspected. Bounded arc-length resampling preserves the peaks of long gestures without depending on device report rate.

Deletion uses actual transformed ink against the gesture path and small convex regions between adjacent passes. It fills the gaps between zigzag legs without erasing the whole bounding box. Short legs and exit tails retain their direct crossing coverage. Disconnected dots/crossbars are compared in the word's orientation and attached nonrecursively; rotated long word boxes cannot turn adjacent letters into apparent tiny marks. Typed content, images and standalone equations remain excluded. Held encircle selection takes priority, opt-in defaults stay unchanged, and erase/undo/redo is one operation.

Regressions include synthetic approximations of the three reported scribbles, rounded/unequal passes, fragments inside swept gaps, footprint corners and neighboring lines/words, long/slow gestures, sparse/dense reports, mouse/tablet events at multiple zooms, rotated detached marks and undo/redo/reload. These are geometry/controller checks, not physical pen recordings. A repetitive wave deliberately drawn across existing writing remains inherently ambiguous with a scrub; the overlap gate protects empty-space writing and incidental contacts, not every possible handwriting intention.

Two additional fixtures trace the white gesture and visible blue ink directly from reported screenshots: large rounded scrubbing across multiple lines and unequal rounded scrubbing across a single line. Raster centerlines are simplified within 0.8 pixels and visible ink is split at junctions. These verify triggering against screenshot geometry; a screenshot cannot recover pen lifts, timestamps or occluded ink, so they do not establish complete original-letter deletion.

For local testing, close Folio normally and run `cargo run --locked -p folio`, or `cargo run --locked --release -p folio` for the optimized profile. Each command builds and runs its corresponding executable. `target/debug/folio` and `target/release/folio` are separate builds; rebuilding one does not update the other or replace code already running in an open window.

Folio requests client decorations and uses the document tab strip as its title bar. The + picker follows the last tab; tabs scroll when space runs out, while the picker stays visible and minimize, maximize/restore and close stay at the far right. Empty-space presses start compositor-driven movement; double-click toggles maximize and right-click opens the native window menu. Tabs consume their own presses and retain drag reordering. ## Offline solving and live math

The independent CPU SymPy service supports selected-problem solving, guided steps, systems/inequalities/calculus, page variables, linked results, explicit function graphs, next-step checking and reviewed word-problem templates. Computation, LaTeX rendering and PDF/image preparation run outside the UI thread. Cancellation, captured source objects, variable snapshots and page/PDF identity prevent stale results from being inserted. Live handwriting regions wait for pen-idle input.

The native panel renders vector formulas and keeps editing, copying and insertion separate. Worked insertion is one durable command; edited results insert as static Equation objects. Keyboard shortcuts do not switch drawing tools while a math field is focused.

### Using the solver

Select a problem and choose **Solve**, or open **Document actions → Math solver**. Review the recognized problem or enter an equation directly, then choose **Solve problem** or press **Ctrl+Enter**. **Solution**, **Graph** and **Check work** expose their inputs. The operation dropdown starts at **Automatic**; target variable, domain and angle convention are under **Settings**. Empty inputs offer **Try example**. Separate system equations with semicolons or newlines; a trailing `=` evaluates an expression, and `?` represents an unknown.

**Guide me** shows one step at a time with Previous/Next/Hint controls; **Show all steps** restores the complete trace. **Copy LaTeX** and **Add answer** remain pinned. **Add options** offers **Answer and steps** and eligible **Live answer**/**Live graph** variants. Inserting answers or worked steps preserves the source and supports undo, redo and reopening. **Edit LaTeX** opens a separate editor: Apply accepts the draft, Cancel editing discards it, and invalid rendering retains the last valid report. Applied edits become static results without computed verification claims, teaching steps or live dependencies; re-solving restores a computed report.

Define `a := 5` and `b := 3*a` using **Define variable**, **Preview variable**, then **Add variable**; explicit `:=` definitions also work through Automatic. Calculate `a+b=` and choose **Add options → Live answer** to link the result. Definitions apply across the current page, independent of spatial order. Duplicate names, cycles and unresolved dependencies produce errors. Editing a definition recomputes downstream results. A live answer tracks selected typed text only while that text remains its expression; entering a different problem creates an independent calculation.

Live handwriting watches a bounded source region after a 700 ms pen-idle delay. Manual expression/definition editing detaches that region. Live scans process up to 32 results with fair rotation. Explicit `y=f(x)` graphs use adaptive real sampling on a CPU worker and persist their range and page variables. Graph display follows the current paper and theme while preserving source SVG geometry and export colors.

In **Check work**, type a next equation or choose **Use handwritten step**, then **Check next step**. Equation comparisons check solution sets, including lost roots; expression comparisons retain domain restrictions and can be conditional. Unsupported comparisons return unknown rather than treating numerical samples as proofs. For photographed problems, select one Image and use the crop tool; PDF regions use normalized left/top/width/height values in [0,1]. Word problems use supported deterministic templates and require review followed by **Solve this equation**.

### Engine, setup and limits

`crates/app/src/math_solver.rs` controls a bounded JSON-lines Python service with pinned SymPy 1.14.0 and mpmath 1.3.0. A restricted parser retains source spans and domain restrictions. The service uses no Torch or additional neural model, blocks Internet sockets, caches repeated requests and kills obsolete work on cancellation. The configured computation limit defaults to 8 seconds where supported; the Rust response deadline is 15 seconds. Platforms with Python's `resource` module also enforce a 768 MiB virtual-memory limit. LaTeX parsing and vector-outline conversion run outside the UI thread.

For a development pack, install `scripts/math-solver-requirements.txt` in the chosen Python runtime, then run `python3 scripts/setup-math-solver.py`. Lookup order is `FOLIO_MATH_CONFIG`, `<data-dir>/math-solver/pack.json`, bundled resources, then `artifacts/math-solver/pack.json` for debug builds. The pack retains dependency notices; update Python paths if moving a separately prepared pack. OCR uses its own recognition pack and settings.

Copy/paste and duplication remap math sources; pasting a calculation without its handwriting source detaches the watched region. Current document/database compatibility is described under [Persistence and recovery](#persistence-and-recovery).

Supported arithmetic, algebra, systems, inequalities, derivatives and integration expose steps where available; advanced results may have labeled summaries or explicit errors. There is no symbol-to-stroke alignment, per-subexpression highlighting, implicit/3D graphing, arbitrary word-problem reasoning, general proof checking or universal teaching trace. Handwriting and image recognition require review. Controller routing tests isolate integration from OCR accuracy; synthetic GUI checks do not establish physical input reliability.

## Explicit offline recognition, copy and replacement

Text and math recognition share a resident GLM-OCR backend for handwriting, image crops, PDF regions and solver/live-math input. Automatic native setup supports x86_64 Linux and Windows. An explicit first-use choice downloads Q8_0 language/vision weights and the llama.cpp Vulkan runtime from Hugging Face and GitHub over HTTPS: approximately 1.47 GB, with about 1.56 GB installed on Linux including the retained runtime archive. No CUDA toolkit or Python OCR environment is downloaded. Exact revisions, platform-specific sizes and SHA-256 digests are maintained in `crates/app/src/recognition/native.rs`.

### Recognition setup and privacy

Downloads are resumable and checksummed. Cancellation retains `.partial` files; retrying recognition resumes setup. Checksum failures discard corrupt partials, and only verified assets become active. Setup is serialized with a file lock and uses safe staged extraction. At launch, a background worker verifies an existing native pack and discovers eligible Vulkan devices once, without downloading assets or loading the model. Successful preparation is retained for the library session: cancellation, server restarts and CPU fallback reuse it without hashing files, extracting the runtime or probing devices again. Missing or corrupt packs still go through verified setup on an OCR request; first-use setup caches its results too. Restart Folio after changing native pack files or device preferences. Warm requests reuse the resident model. After five minutes without a queued or running request, the model process stops to release its RAM and GPU memory; existing review results remain available. The next request reloads the model using retained preparation, adding model startup time. Progress appears in recognition controls and accessibility status. Cancel/Esc invalidates pending results and stops the model process.

The backend prefers full inference on an eligible discrete Vulkan GPU, then other eligible devices. If full GPU loading fails, it tries memory fitting: the runtime accounts for image-encoder weights, keeps the 16,384-token context, targets an additional 1 GiB of GPU memory headroom and places language layers and their attention cache in system RAM as needed. CPU-assigned language operations stay on the CPU. If fitting still fails, it tries the image encoder alone on the GPU, then CPU-only recognition. GPU discovery includes devices with at least 1.25 GiB free; this is a candidate threshold, not a guaranteed memory requirement. Fitting uses current runtime memory availability rather than the cached discovery budget.

A GPU inference connection/server failure follows the same bounded progression through lower-memory modes, ending with one CPU attempt; invalid input and truncated output remain errors. Status distinguishes memory fitting, GPU image encoding and CPU execution. Full GPU inference uses the same device for language and vision; mixed modes retain GPU image encoding while language work can run on the CPU. NVIDIA and AMD have recorded smoke checks; Intel remains unverified. See [WINDOWS.md](WINDOWS.md#optional-ocr) for Windows-specific guidance.

Images stay local. The inference server binds to loopback with a random API key, bypasses HTTP proxies, disables its web UI and loads models offline. Internet access is needed to fetch assets, not for subsequent recognition. Source ink is rendered as black rounded strokes on white with supersampling; image transparency is composited onto white. Model attribution and runtime licenses/notices are retained in the pack; see [LICENSES.md](LICENSES.md).

Pack lookup checks `FOLIO_RECOGNITION_CONFIG`, `<data-dir>/recognition/pack.json`, then a usable portable pack beside the executable's `bin` directory. Valid existing Python packs remain supported. An explicit Python pack override reports missing files instead of being automatically replaced. Text/math recognition smoke checks establish execution, not general handwriting accuracy; review recognized content before insertion.

Results open an editable review. Copy leaves the document intact. Replace writing removes only captured strokes and inserts editable text or a rendered equation in one journaled command. Math validates and renders before changing the page; failure restores the corrected review and retains the ink. Note/page/source identity is checked before accepting and replacing, and generations reject cancelled responses. Original sensor data stays in durable undo history.

Digit-only handwriting lines use the captured stroke layout to remove false spaces inside compact numbers, for example `1 2 3 4` → `1234`. Correction requires one separable ink group per recognized digit on a shared line. Unequal heights and uneven baselines are accepted when the common vertical band covers at least half the shortest digit and every digit is at least 40% of the line height; tiny ambiguous marks are excluded. Gaps no larger than 35% of the line height are joined. Wide gaps remain separators. Ambiguous or overlapping glyphs, mixed text/formulas, tabs, line breaks and image/PDF recognition retain the model's spacing. This applies to text and math suggestions from both native and Python packs, before review; user edits are retained as entered.

Keeping ink and indexing the reviewed text makes handwriting searchable without replacing its strokes. Editing or deleting a source invalidates its reviewed index; undo restores it. There is no automatic text detector.

## Rendering and persistence performance

UI maintenance polls every 250 ms while idle. Native accessibility actions wake the UI through an asynchronous channel. Input, new animations and background requests made during rendering or virtual-row layout resume 16 ms polling, which continues during active interactions, animations, background work and update checks. Pending save receipts retain fast polling; failed saves and recognition awaiting a download choice do not keep an otherwise idle editor at frame rate. Dropping the view cancels its polling task.

Window-control glyphs use cached SVG alpha masks with their original optical geometry, so a few title-bar lines do not trigger full-window path antialiasing. The Linux Blade renderer allocates its path/resolve and multisample textures only when a scene contains vector paths. Resizing a library-only window does not allocate those targets. Existing targets retain resize hysteresis; replacements wait for GPU completion and are created only if a later scene needs them. Drawing keeps its configured antialiasing sample count. Targets already used by an editor remain warm until resize or window destruction; returning to the library does not reset every renderer/font cache. Compare base RAM before opening any editor in release builds: debug code pages and software-driver allocations can account for much of the apparent startup footprint.

Finite-page stack layout is shared by painting and navigation and rebuilt only for page structure or dimension changes. Autosave and accessibility share command-aware searchable-text snapshots; geometry-only edits reuse them while text, reviewed-handwriting and source-visibility changes invalidate them. Text hit testing visits spatial candidates in drawing order. Bulk spatial edits rebuild dense buckets once and retain measured bounds for unchanged text. Multi-page command application indexes page identities lazily and resets that lookup after structural changes; autosave deltas cache page lookups and index only after repeated scans justify it. Ordinary incremental saves reconcile touched pages; structural/full snapshots reconcile the complete page identity set. Page duplication avoids copying maps and drawing order that it immediately replaces.

Library startup defers loading editor documents and their undo journals until a document is opened. Loading shares identical immutable raw/path buffers across current ink, erased fragments and undo snapshots, comparing every sensor bit; the persisted format and complete undo history remain intact. Closing a durable tab releases its session and object previews, including the last editor tab. A bounded view-state cache remembers page, zoom, pan and rotation for up to 128 released notes during the same app run, independently of the restart preference. Unsaved edits, failed saves, deferred actions, background imports and equation renders retain their sessions until safe. Inactive sessions use an estimated 96 MiB model budget and an eight-session limit; the active session remains resident. Cover page models retain up to 48 recent entries. Estimates count shared ink buffers once and are cached until the session changes. Loading an editor removes its separate cover model. Ink-only previews, batches and PNG exports avoid initializing the export font database; text and embedded SVGs retain font support.

The folder sidebar renders visible rows, with collapsed descendants excluded before layout. Editor accessibility updates bypass folder indexing when no folder labels are requested. Hierarchy order and identity lookups are shared, and path labels are resolved on demand with a 16 MiB retained-text budget. Accessibility removes offscreen probe rows after scrolling. Folder arrow navigation uses the complete expanded tree and scrolls/focuses offscreen destinations, including wraparound. Long text fields paint visible rows and reuse shaped-line width and binary caret lookup. Native glyph/emoji painting rejects clipped raster bounds before populating the GPU atlas. Export and solver graph previews release replaced/closed GPU images. Atlas textures retire after their last submitted GPU frame, and abandoned uploads are removed before texture identities are reused. Freed image tiles return their atlas allocation on Linux and Windows even when neighboring images remain resident. Recovery awaits its background task without idle polling, successful settings/folder writes leave the retry queue immediately, and offline subprocess deadlines include blocked input writes while output pipes continue draining beyond the retained diagnostic limit. Each offline call owns a Unix process group or nested Windows job; normal worker descendants inherit this ownership and are terminated before pipe threads are joined. Windows workers join their cleanup jobs before executing, so fast launchers cannot spawn helpers or exit before ownership is established.

Ordinary edits update only changed spatial-index entries and the source references of derived shapes/equations. Reference counts keep an original stroke hidden when several derived objects share it, including after undo/redo. Command application no longer scans every page to restore drawing order; appended ink keeps its existing order, while insertion/deletion restoration remains exact. Batch deletion filters each affected page's drawing order once, and undo merges distinct insertion positions without shifting the remaining objects repeatedly. Mixed delete/insert commands defer unrelated removals until the end of the command, avoiding repeated order scans when replacing strokes with fragments. Reusing an object identity removes its old order entry immediately. Page replacements preserve their sequence; equal insertion positions retain stable insertion behavior. Session drawing-order ranks update incrementally for appended objects and are rebuilt for removals or middle insertions. Sparse copy, edit, recognition and math-panel actions use those ranks to visit only selected objects and any required source strokes; dense selections follow page order without sorting. Recognition eligibility reuses indexed hidden-source counts instead of scanning unrelated objects. Small object transforms that stay in the same grid cells update exact bounds without replacing cell memberships. Dense spatial queries choose a bounds scan before hashing repeated cell references; sparse indexes retain one grid pass.

The renderer caches the ordered visible object set with a small margin equivalent to 64 logical pixels at the current zoom. Small resize and pan steps reuse both that set and its ink batch plan; leaving the cached area, changing content/index bounds or substantially shrinking the viewport rebuilds it. Canvas transforms and clipping still follow each frame's exact bounds, preserving ink scale and revealing newly exposed content. Dense visible sets follow page order directly; sparse sets sort only visible candidates by their cached ranks. Completed path-cache maintenance runs when that set changes rather than on every pen frame. Unrotated paper and its shadow use GPU rectangles; ruled and grid backgrounds cache thin rectangles per viewport/theme/display density. Fractional device-pixel edges use weighted coverage to preserve line thickness during resizing and on scaled displays. Rotated pages and dotted backgrounds retain compound paths, removing paper's full-viewport path-rendering pass from ordinary blank, ruled, grid and PDF pages. Background spacing doubles as needed to keep marks at least 16 logical pixels apart when zooming out, bounding infinite-canvas geometry by screen area; retained dots stay on the original document lattice. Dots use direct convex triangle fans instead of tessellating disconnected contours together. `cargo test -p folio-ui benchmark_infinite_paper_zoom_out -- --ignored --nocapture` compares CPU path tessellation and rectangle preparation during pan at several zoom levels, not GPU frame time. Object previews share their immutable BGRA buffer with the GPU image wrapper instead of retaining a second CPU copy. Theme adaptation allocates only when a pixel color actually changes; recolored graphs retain their separate rendering. These conversions run on GPUI background tasks, with at most two in flight. GPU uploads still require their own device storage. Rendering rejects stale source objects, pixels and theme results. The controller trims preview/session caches every 250 ms instead of scanning them every UI tick. Worker results are bounded to eight items rather than 64, limiting queued decoded-image accumulation; this is not a bound on total application RAM.

The thumbnail cache holds up to 48 entries and renders at most two replacements concurrently. Eviction and content/theme invalidation remove old images from the GPU sprite atlas as well as the Rust cache. Object-raster replacement, offscreen eviction and page eviction release their atlas images too. PDF prefetch keeps visible pages and a small neighboring working set; distant decoded assets and their uploaded images are released together. Opening the library releases editor page geometry, ink/object images and decoded PDFs. Reopening the editor rebuilds its visible canvas caches.

The renderer caches consecutive settled ink on Linux and Windows in ordered batches of up to 32 strokes. Two background raster jobs run at most per visible page; cached images are limited to 16 million pixels per visible page and one million pixels per batch. Device-pixel density is preserved, and oversized batches use vectors. Selection, erasing, object changes, themes and display density invalidate affected batches immediately; stale jobs cannot replace current ink. Dropped pages/images release their atlas entries. Live ink and exports remain vector-based. The isolated `cargo run --release -p folio-ui --example ink_layers` fixture exercises default caching, selection, theme and zoom invalidation, including 60 window grow/shrink steps, rotated infinite dotted paper down to 10% zoom and canvas cache release/rebuild when visiting the library, without opening installed update caches. It defaults to 1,024 strokes; `FOLIO_INK_FIXTURE_STROKES=4096` exercises a denser page. `cargo test --release -p folio-ui benchmark_dense_saved_ink_scene_preparation -- --ignored --nocapture` measures CPU scene geometry and resize culling/batch preparation, not GPU frame time or physical input latency.

The Linux Blade backend uses a frame upload pool for path geometry and image staging. Buffer capacities grow geometrically; completed smaller buffers are released when replaced, and unused buffers retire after a short reuse window. GPU completion gates both reuse and retirement. Dense writing therefore does not retain every preceding upload size, and leaving a large scene releases its unused upload capacity. Device-free pool regressions cover growing scenes, shrinking working sets, alignment and in-flight buffers. Native dense-page smoke checks use software Vulkan on a private X11 display; they do not establish physical pen latency or guarantee recovery from an unrelated GPU-driver failure.

Scratch erase accepts sustained advancing up/down scrubs across existing writing, without requiring horizontal return passes. It still requires broad reversals with deliberate turnarounds, rejects smooth waves and ordinary W/M handwriting, targets actual ink crossings and remains one undoable operation.

Preview completions/errors for edited, deleted or evicted objects are discarded. Edits, undo and redo release obsolete cached pixels and failed-preview source references immediately; ordinary object edits check only their own cache keys. Page replacement and deletion release stale previews on the affected pages while preserving unchanged sources. Cover changes release old session snapshots before another library request, and editing a loaded note discards its separate library preview. Offscreen-page results cannot insert their bounds into the active page's index. Higher-resolution previews are retained when a smaller render budget would already suffice. Repeated document-load requests are coalesced, and a failed queue submission no longer leaves a tab indefinitely pending. A failed held-pen shape fit runs once until the pen moves substantially, preventing repeated stationary fitting; endpoint tremor tolerance and continued drawing/shape recognition remain intact. Saturated grid-cell counts use checked arithmetic; extreme imported coordinates and non-finite query bounds cannot overflow the index or cause huge grid allocation.

CPU benchmarks measure command application and spatial-index maintenance separately from drawing, persistence and presentation; their reductions must not be read as equivalent improvements in physical pen latency. Full-document save/load still scale with document size.

## Tablet incident — 2026-10-03

Latest outcome: the user reports that the tablet works normally after a restart. No permanent compatibility service or Bluetooth configuration change was installed. Leave the optional helper off while normal operation continues. The short sniff-disable trials describe the affected session; they do not establish that future sessions need a workaround. The restart's scope and subsequent stable duration were not captured, so the exact cause and lasting resolution remain unconfirmed.

Real Intuos BT S testing exposed an abort missed by synthetic smoke replay: the Wayland pad group child event was registered as opcode 1 instead of 0. The hotfix uses generated protocol opcode constants for all tablet child registrations. `scripts/verify-tablet-protocol.py` executes those registrations against the protocol's child-event metadata using a private socket pair, without connecting to GNOME or input devices. It fails on the earliest development build and passes all six child events with the fix. Those early development packages were withdrawn; their synthetic input checks did not establish real-device stability.

The user's GNOME/Mutter 50.5 also crashed twice after Folio had exited. An October 1 core has the identical fault offset (`libmutter-18.so.0 + 0xa9e61`), while this project's files were created on October 3; the same compositor fault had occurred before Folio. Both cores resolve to `meta_wayland_tablet_update_sprite` writing through a null current tablet during proximity-out, after Bluetooth tablet reconnects. System input/GNOME package checksums are intact, their installs predate this work, and no Folio service, system driver, udev/Xorg rule or global accessibility setting was installed/changed. Root cause of the Bluetooth proximity sequence remains unresolved; fixing Folio's child-event registration does not fix this compositor failure or exclude an indirect trigger in the affected session. No system package, driver, pairing, GNOME extension or desktop configuration was reset by the agent.

The incident-era X11 launcher workaround is retired. The current launcher prefers native Wayland; `FOLIO_FORCE_X11=1` selects X11 for Folio's process only. Backend selection does not prevent GNOME from processing Bluetooth proximity events while Folio is closed. Native Wayland hotplug remains unverified on physical hardware.

Live diagnosis established Bluetooth link timeouts with Folio closed. USB runtime state was active at the observed drops and suspended afterward; GNOME stayed alive in the later sessions. An HCI trace showed one link becoming silent around sniff-mode entry and timing out, while a subsequent active link delivered 2,243 reports over 41.4 seconds. Sniff mode is now the primary hypothesis, with the exact controller/remote-firmware/RF cause unresolved.

The corrected per-connection experiment **completed on physical hardware**: handle 11 changed from policy 0x000f to 0x000b (only sniff disabled), survived 60 seconds, delivered 2,995 reports, and restored 0x000f with successful controller readback. The user confirmed the tablet disconnected by itself after the command finished. The post-restoration disconnect occurred outside the HCI trace, so its exact reason/time are not captured.

The user then ran the foreground helper on handle 12. Its log confirms policy 0x000f → 0x000b at 19:04:01, followed by restoration to 0x000f when interrupted at 19:05:22 (81.896 seconds). The user reported normal tablet operation throughout, failure immediately after stopping, and failure on reconnecting without the helper. Two short interventions now support a repeatable temporary workaround. The helper was configured for one hour but interrupted after about 82 seconds; one-hour stability, the exact faulty component and GNOME crash prevention remain unverified. These observations do not establish how the session became unstable or exclude an earlier indirect Folio trigger.

`scripts/keep-tablet-active.py` provides an optional foreground helper scoped to this Intuos address. It keeps the sniff bit disabled on that device's connections for a bounded session (default one hour), restores the current link's original sniff bit on normal/interrupted exit, and preserves other policy flags. It never connects/scans/resets, changes adapter defaults, installs services or edits persistent settings. It logs policy metadata only. Native policy changes and interruption cleanup were verified in the hardware trials; long-session helper behavior remains unverified. A root-owned runtime lock prevents duplicate helpers. Linux requires sudo for the HCI policy interface.

Twenty simulated safety tests cover pending/reserved handles, device identity, rollback, interruption, link loss/reconnect, policy drift, other-bit preservation and duration expiry; native ABI was independently checked with a C harness against upstream headers. The first experiment's pending-handle I/O error was a diagnostic bug and was fixed before the successful trial. Read-only utilities remain available for raw tablet events, BlueZ disconnect signals and private HCI traces. HCI traces contain pairing-key material and remain local/private. No Bluetooth reset, pairing/driver change or persistent compatibility service has been applied. See [incident report](artifacts/incident/REPORT.md) for exact evidence and limits.

## Architecture

The workspace separates `apps/desktop` and `app`, `ui`, `input`, `ink`, `canvas`, `document`, `storage`, `gestures`, `shapes`, `math`, `pdf`, `search`, `export`, and `platform` crates. Rust 1.92+ is required by the subset-font PDF backend. Ink, geometry and structured documents have no GPUI dependency. The UI forwards operations to a controller; document mutation and LaTeX rendering are outside the presentation layer. Explicit optional recognition lives in `app::recognition`, with a resident native Q8 backend and support for existing Python packs; no automatic text detector is present.

Native Linux GPUI patches provide Wayland tablet-v2 frames, tablet pads and pointer pinch gestures, and XInput2 pressure/tilt. Six pen styles share an incremental pressure/velocity filter and vector outlines. Raw and processed vectors are shared immutable arrays so transformations and undo do not copy sensor buffers. Raw samples survive smoothing, transforms, segment erasing, shape/equation conversion and refinement. Each erased fragment keeps original sensor samples plus an independent visible path.

Completed paths are cached; opaque active ink is divided into 256-point chunks with a bounded mutable tail. Translucent active ink uses one compound fill for consistent overlap opacity. A uniform-grid spatial index updates changed objects and derived-source reference counts and culls offscreen content. Visible objects remain in cached document order across small viewport changes; content/index changes and movement beyond the retained margin refresh the set. Paper geometry is also cached. Images, text and equations use bounded worker-generated previews; GPUI transforms those raster sprites on the GPU, keeping them aligned with vector ink during pan, zoom, resize and rotation.

Message-passing workers separate persistence, document/rendering processing and search/load. Each expensive processing queue holds at most 16 jobs; the result channel holds eight items. GPUI pixel preparation has a separate two-task bound. Search generations coalesce obsolete search jobs. Persistence uses a 64-item channel; saturation or disk errors retain the live document and bounded command history for a full retry rather than blocking pen input or accumulating failed deltas indefinitely.

## Persistence and recovery

SQLite uses WAL, `synchronous=FULL`, foreign keys, stable UUIDs, per-object rows and atomic document/search/journal transactions. Schema version 6 adds an indexed, stable page-to-FTS-row mapping independent of SQLite page rowids, plus note/page-position and draft indexes. Every writer open upgrades older databases transactionally; versions 3–5 retain their existing valid FTS rows, while older databases first rebuild legacy OCR search content. Earlier builds reject schema 6. Search updates use rowid lookups and skip unchanged content. The current document format is 4. Format 3 introduced optional math links alongside the version 2 cut-path and character-group records; earlier document formats remain readable. Editing upgrades the format, and clipboard writes use V2 while accepting V1. Each history holds at most 512 commands; full catch-up saves replace its journal consistently with the current live state.

Normal edits write changed objects and affected page headers/FTS rows. Metadata-only edits update searchable titles/tags without rebuilding every page. Active ink drafts are saved approximately once per second. Completion clears the draft in the stroke transaction. Periodic SQLite snapshots retain three generations. Assets must be backed up with the database.

Recovery never overwrites or renames the original data. It prefers a healthy checkpoint, otherwise salvages independently readable records into a new sibling directory, copies assets, and writes `RECOVERY.json` with issues. Asset maintenance considers current documents, undo history and retained snapshots and moves unused files to `orphaned-assets`; it does not permanently delete them. Damaged snapshots stop maintenance rather than guessing references. Save errors remain visible and retry from the retained live document.

## Validation and measurements

Run `cargo test --locked --workspace -- --test-threads=2`, `cargo fmt --all -- --check`, and `python3 scripts/check-documentation.py`. Workspace tests cover document compatibility, raw-data preservation, ink/gesture geometry, undo/redo/reopen, storage recovery and rollback, search, recognition review, solver cancellation and stale results, and UI cache/field behavior. Native smoke replay and accessibility checks use private desktop sessions and throwaway documents; synthetic checks do not establish physical tablet reliability.

Reproduce CPU measurements with `cargo run --release --locked -p folio-app --example benchmark -- 10000` (also use `50000`). Command application, spatial updates, initial save and load are separate measurements; they exclude GPU presentation, compositor and physical-device latency. `FOLIO_PROFILE_INK=1` reports dispatch-to-CPU-paint timings. `FOLIO_PEN_RECORD=/new/path.jsonl` records rich pen frames asynchronously; a bounded queue drops diagnostics instead of delaying ink. Keep generated evidence under ignored `artifacts/validation/`.

`cargo run --release --locked -p folio-app --example benchmark_controller -- 10000` (also use `50000`) measures loaded library covers, single-object copy/move, recognition eligibility, opening the math panel for selected text, deferred edits, and deletion/replacement/undo of alternating objects. Deletion, replacement and restoration time document command application only; they exclude controller indexing, persistence and drawing. Math-panel timing excludes solving, OCR and rendering. The fixture checks that repeated restoration preserves objects and drawing order.

The controller benchmark also measures mouse text hits in ink-heavy pages. `cargo run --release --locked -p folio-app --example benchmark_background -- 10000` measures database opens, variable lookup, continuous navigation through 10,000 finite pages, autosave-delta construction for 512 changed objects on the last page, and a small edit/save on the first two pages. `cargo run --release --locked -p folio-canvas --example performance` includes dense-cell deletion/undo alongside geometry kernels. These are CPU measurements on generated fixtures; use the same machine and build profile for comparisons.

For RAM comparisons, use matching build profiles, a private desktop and copies of the same fixture. On Linux, record RSS/PSS from `/proc/<pid>/smaps_rollup` at library startup, after the editor finishes loading, after durable undo/redo, and after closing the tab. Include blank and history-heavy notes. Wait for asynchronous loads and saves before sampling; a loading overlay is not a settled editor. Software Vulkan places driver/image allocations in system RAM, so its absolute footprint does not predict hardware-GPU usage. Released model allocations may remain in the process allocator; validate ownership release as well as RSS.

## Remaining validation and technical limits

- A physical Intuos BT S was used for incident and OS transport/policy testing. Folio's physical pen rendering and measured 120 Hz hardware-to-display latency remain unverified. Palm rejection, HiDPI tablet calibration, pad layouts and hardware button mappings need further device trials. The app suppresses pointer emulation during pen proximity; the compositor remains responsible for rejecting native touchscreen palm contacts.
- Native work is verified on this Fedora GNOME Wayland/Xwayland session, with builds/tests also run in Debian bookworm. COSMIC, KDE, other distributions, screen-reader workflows and HiDPI sessions require their own runs. Packaging and AT-SPI interfaces do not substitute for certification.
- Original PDF objects are preserved, but digital signatures become invalid when an annotation export changes the document. Complex multi-source named destinations, conflicting form resource/name dictionaries and unusual PDFs need broader corpus testing. The original retained files remain intact. Preview resolution is bounded; vector originals are retained for PDF export.
- Pixel previews use a 128 MiB controller cache and adapt to the visible working set. Model budgets are eviction targets, not a cap on application RAM: active/unsaved documents, allocator retention, fonts, GPU/GPUI images and visible geometry have additional costs. Extremely large visible geometry still requires GPU profiling. Dirty note sessions are retained instead of evicted when saves fail or autosave is disabled.

Priorities are physical pen trials, larger ink workloads and PDF corpus evaluation, then cross-desktop/distribution and assistive-technology certification. No account, network service, proprietary SDK or sync backend is required.
