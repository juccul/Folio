# Development status — Folio 0.2.6

Updated 2026-11-24. Folio is a runnable Rust Linux and Windows desktop application. Since 0.2.6 its interface runs on [Rune](https://github.com/anomalyco/rune), which replaced GPUI (see [Rune presentation layer](#rune-presentation-layer)). Production certification still requires physical tablets and additional desktop/distribution sessions; synthetic events and CPU benchmarks do not establish hardware-to-display latency.

Version 0.2.6 replaces the GPUI interface with Rune: the interface and canvas draw on the GPU, startup is faster, memory use is about half of 0.2.5 and idle windows stop drawing. It adds the full-window tour (shown once per tour version, `Settings::tour_version`, to fresh and upgraded libraries alike), menus and dialogs that morph in place, title-filtering library search and the sidebar glide. Database schema 6, document format 4, the signed update manifest and the release asset names are unchanged from 0.2.5, so existing installations update in place. Windows setup/portable and signed Flatpak packages share the same release source. See `WINDOWS.md` for Windows Ink support and validation limits.

## Rune presentation layer

`crates/ui` builds the whole interface with Rune (pinned to a `dev` revision in the workspace `Cargo.toml`, together with the `[patch.crates-io]` entries Rune requires). It builds with the stable toolchain (verified with Rust 1.97) and, on Linux, needs the `libxkbcommon` and `libwayland-client` development packages at build time.

- **Views.** `compat.rs` keeps the GPUI-style vocabulary the views were written in (`div()`, inherited text styles, block layout, `cx.listener` handlers, actions and key bindings) and builds plain Rune elements from it each frame. The view state lives in one `NotesView`; Rune re-runs the view after every handler. Layout changes land at once (`instant_changes`), as GPUI drew them; colours keep Rune's motion. `executor.rs` runs GPUI-style `cx.spawn` futures on the UI thread before each frame and `background_executor()` work on threads of its own. Finished background work wakes the window and a waiting timer schedules a wake at its deadline, so pending tasks no longer poll at 60 Hz, and running ink rasters no longer rebuild the view every frame (each notifies as it finishes).
- **Canvases.** Pages, page thumbnails and small painted controls (tool wheel, colour tracks) keep GPUI's immediate-mode painting calls, which `paint.rs` records as a display list. Quads (paper, rulings, page shadow, selection boxes) and images (cached ink batches, dot-paper tiles, PDF backgrounds) become Rune elements composited on the GPU; quads are matched by their place in the list, so the list lands every change at once, colours included (`Spring::NONE`): a click's animated commit faded a PDF page's white paper into the next page's ruled lines; each image uploads once and then only moves, so panning and zooming cost no CPU raster. When a zoom crosses a raster density, each old image stands in for its batch until the new one is ready, so ink never falls back to vectors mid-zoom, and the conversion to upload pixels happens on the raster thread. A run of fewer than eight strokes gets an image too once it holds 1,500 path points (one long scribble). Ink too large for one image (seen up close) is split into tiles of about a megapixel on a power-of-two grid in document space, nearest the view first; the tiles replace the vectors once every tile in view is ready, and until then the whole image from before the zoom stands in, stretched. Ink without a cached image (the stroke being written, new, selected or erased ink) is drawn by the GPU as round-capped segments from its centreline; the stroke being written is drawn as lifting the pen would commit it (`StrokeBuilder::finished_path`: the straight catch-up from its stabilized end to the pen, and the fountain/pencil end tapers), so it no longer changes on release; translucent ink fades as one layer so overlaps blend once. Canvas text is rasterized once per layout into an image the GPU moves; after a zoom or rotation the old image is stretched until the change rests for 140 ms. Remaining paths are rasterized with tiny-skia in runs no larger than their bounds, in paint order. A run of solid-colour fills and strokes is fingerprinted and, when it paints what it painted last frame (the pen cursor, a rotated page's paper and shadow), reuses its image without rasterizing; other unchanged runs are not uploaded again. Release builds optimize tiny-skia for speed. Canvas text uses usvg, as export does. `FOLIO_PROFILE_CANVAS=1` prints each canvas paint time and each view build time.
- **Input.** Shortcuts dispatch from Rune's window key handler to the actions the view registers. The canvas takes pointer drags (left and middle button), hover, wheel, pinch (`on_magnify`, applied as an exponent so a fast Ctrl + wheel cannot reach a zero or negative zoom), touchpad rotation (`on_rotate`, about the fingers) and the secondary button. Pinch and rotation are ignored over dialogs, during strokes and while a pen is in range. Dropped files import as before.
- **Tablets.** Rune's winit is vendored under `vendor/winit` with a tablet extension (`winit::platform::tablet`): Wayland `zwp_tablet_v2` tools and pads, X11 XInput2 pressure/tilt valuators, and Windows Ink `WM_POINTER` pen history. Each pen report publishes normalized pressure, tilt in degrees, twist, eraser identity and barrel buttons, then emulates cursor movement and the left button so controls work with the pen. `tablet.rs` queues the reports, wakes the window and hands every sample to the view at the start of the next frame; the canvas ignores the emulated mouse while a pen is in range or reported within 200 ms. While a pen is the active input (`tablet::pen_active`), text fields that a pen action opens (a rename, the picker, find, a recognition review) take no focus of their own (`compat::apply`): GNOME opens its on-screen keyboard for any focused field after pen input. Tapping a field still focuses it, and text placed on the canvas still takes focus (`FocusHandle::focus_for_typing`). A pen press that lands on the selection toolbar is left to its emulated click: the canvas ignores that press until the pen lifts (`NotesView::over_canvas_control`), where it used to clear the selection and take the toolbar away first. `folio_input::ForceAngle` maps force to `0.05..1` between a 2% resting floor and a 98% ceiling (devices without pressure and the mouse draw at 0.6), and limits combined tilt to 80° in its direction (devices without tilt report upright). `folio_input::PadInput` maps express keys to the configured pad actions, rings to zoom (`e^(0.01·degrees)`) and strips to scrolling (800 points per strip length). The lower barrel button opens the tool wheel (Settings can turn this off) and the upper one erases. On Windows, pens no longer arrive as touches, which panned, waited for an 8-point slop and opened a context menu after a 0.5 s hold. X11 barrel buttons and pad express keys no longer click; pad rings and strips stay wheel events there. Wayland tool cursors follow the window's cursor through `wp_cursor_shape_v1` where the compositor offers it. Wayland touchpad pinch and rotation arrive through `zwp_pointer_gestures_v1`. `WINIT_WAYLAND_NO_TABLET=1` leaves tablets to the compositor's pointer emulation.
- **Window.** On Windows and macOS Rune keeps the window controls over Folio's tab-strip title bar. On Linux Folio draws the whole frame again, as with GPUI: the vendored winit's `platform::client_frame` drops the system frame (Wayland asks for client-side decorations and skips winit's drawn frame; X11 sets no-decoration hints) while Rune still treats the window as decorated, so it minimizes and maximizes. Folio draws minimize, maximize/restore and close in the tab strip, and 4-point edge and 8-point corner regions resize through the compositor (Rune has no diagonal cursors, so corners show the column cursor); maximized, full-screen and tiled edges have none. Title-bar moves start once the pointer travels 4 points, so a double click reaches Folio and toggles maximize. A secondary click on empty title bar opens the system window menu (Wayland, and X11 window managers with `_GTK_SHOW_WINDOW_MENU`). `FOLIO_SYSTEM_FRAME=1` keeps the system frame. Closing with unsaved edits reopens the window to ask.
- **Headless checks.** Debug builds (and `--features tooling`) take Rune's agent flags, for example `folio --data-dir DIR --open-note ID --snap out.png --size 1440x1000 --scale 1 --at 2`, plus `--script`, `--tree` and `--trace`. Headless GPU runs need a Vulkan driver (`mesa-vulkan-drivers` provides lavapipe).
- **Limits.** The tablet backends are verified by unit tests, type checks (Windows) and synthetic mouse runs, not physical tablets. Pad rings and strips on X11 and pads on Windows depend on the driver's own mapping. Two-finger touchpad translation during a pinch is not applied. Import picks one file per dialog. The GPUI native-event smoke harness (`--smoke-test`) is removed; Rune's headless scripts replace it. A brand-new library with no documents yet can keep the window presenting frames while idle (about 6% of one core in a headless gamescope session); a library with documents, or an open document, idles without drawing.

## Continuous integration

The `Linux and Windows` workflow tests every branch push, pull request and tag,
and can be started manually with `workflow_dispatch`.
New pushes cancel superseded runs on the same branch,
and pull request updates cancel superseded runs for that pull request. Release
tag builds and manually started builds are not cancelled by branch updates.

Rust tests run with two test threads in CI to limit contention between each
controller's storage and rendering workers. Asynchronous worker behavior remains
covered. To use the same limit locally, run
`cargo test --locked --workspace -- --test-threads=2` on Linux or
`./scripts/build-windows.ps1 -Test -TestThreads 2` on Windows. Omitting
`-TestThreads` preserves Cargo's default parallelism for local Windows builds.
Updater, packaging, math protocol and Rust checks have separate CI steps so the
failing check is visible directly in the run summary.

## Scratch erase — current source

Recognition separates a geometric scrub candidate from the decision to erase. Gestures need at least 16 document units of travel along a scrub axis. Compact retracing accepts three broad passes in a corridor no wider than 38% of that span (wider four-pass scribbles must revisit earlier passes) and requires two passes to cross existing ink; advancing up/down scrubs accept six broad legs and require three legs to cross existing non-highlighter ink. Rounded corners, unequal amplitudes, diagonal travel and slow gestures are supported. Both footprint/travel axes and their perpendiculars are inspected. Bounded arc-length resampling preserves the peaks of long gestures without depending on device report rate.

Deletion uses actual transformed ink against the gesture path and small convex regions between adjacent passes. It fills the gaps between zigzag legs without erasing the whole bounding box. Short legs and exit tails retain their direct crossing coverage. Disconnected dots/crossbars are compared in the word's orientation and attached nonrecursively; rotated long word boxes cannot turn adjacent letters into apparent tiny marks. Typed content, images and standalone equations remain excluded. Held encircle selection takes priority and erase/undo/redo is one operation.

Regressions include letter-sized and narrow N/Z handwriting shapes, single incidental touches of neighboring marks, obvious small and word-sized three-pass scribbles, synthetic approximations of the three reported scribbles, rounded/unequal passes, fragments inside swept gaps, footprint corners and neighboring lines/words, long/slow gestures, sparse/dense reports, mouse/tablet events at multiple zooms, rotated detached marks and undo/redo/reload. These are geometry/controller checks, not physical pen recordings. A repetitive wave deliberately drawn across existing writing remains inherently ambiguous with a scrub; the overlap gate protects empty-space writing and incidental contacts, not every possible handwriting intention.

Two additional fixtures trace the white gesture and visible blue ink directly from reported screenshots: large rounded scrubbing across multiple lines and unequal rounded scrubbing across a single line. Raster centerlines are simplified within 0.8 pixels and visible ink is split at junctions. These verify triggering against screenshot geometry; a screenshot cannot recover pen lifts, timestamps or occluded ink, so they do not establish complete original-letter deletion.

For local testing, close Folio normally and run `cargo run --locked -p folio`, or `cargo run --locked --release -p folio` for the optimized profile. Each command builds and runs its corresponding executable. `target/debug/folio` and `target/release/folio` are separate builds; rebuilding one does not update the other or replace code already running in an open window.

Folio uses the document tab strip as its title bar (client-drawn on Linux; see the Window entry under [Rune presentation layer](#rune-presentation-layer) for each platform). The + picker follows the last tab; tabs scroll when space runs out, while the picker stays visible and minimize, maximize/restore and close stay at the far right. Dialogs occupy the area below it, and window controls remain accessible during overlays and document loading. With autosave off, tabs mark documents with unsaved edits, and closing asks to save, close without saving, or cancel.

## Offline solving and live math

The independent CPU SymPy service supports selected-problem solving, guided steps, systems/inequalities/calculus, page variables, linked results, explicit function graphs, next-step checking and reviewed word-problem templates. Computation, LaTeX rendering and PDF/image preparation run outside the UI thread. Cancellation, captured source objects, variable snapshots and page/PDF identity prevent stale results from being inserted. Live handwriting regions wait for pen-idle input.

The native panel renders vector formulas and keeps editing, copying and insertion separate. Worked insertion is one durable command; edited results insert as static Equation objects. Keyboard shortcuts do not switch drawing tools while a math field is focused.

### Using the solver

Select a problem and choose **Solve**, or open **Document actions → Math and handwriting → Math solver**. The problem is shown typeset; **Edit** (or clicking it) reveals its source with a live typeset preview. With **Solve as you type** (solver **Settings**, on by default) the panel solves as soon as a problem is read from the page and again 650 ms after typing pauses, keeping keyboard focus in the field; with it off, choose **Solve problem** or press **Ctrl+Enter**. Recognized math in the review dialog is also typeset by default, with **Edit LaTeX** for corrections. **Solution**, **Graph** and **Check work** expose their inputs. The operation dropdown starts at **Automatic**; target variable, domain and angle convention are under **Settings**. Empty inputs offer **Try example**. Separate system equations with semicolons or newlines; a trailing `=` evaluates an expression, and `?` represents an unknown.

**Guide me** shows one step at a time with Previous/Next/Hint controls; **Show all steps** restores the complete trace. **Copy LaTeX** and **Add answer** remain pinned. **Add options** offers **Answer and steps** and eligible **Live answer**/**Live graph** variants. Inserting answers or worked steps preserves the source and supports undo, redo and reopening. **Edit LaTeX** opens a separate editor: Apply accepts the draft, Cancel editing discards it, and invalid rendering retains the last valid report. Applied edits become static results without computed verification claims, teaching steps or live dependencies; re-solving restores a computed report.

Define `a := 5` and `b := 3*a` using **Define variable**, **Preview variable**, then **Add variable**; explicit `:=` definitions also work through Automatic. Calculate `a+b=` and choose **Add options → Live answer** to link the result. Definitions apply across the current page, independent of spatial order. Duplicate names, cycles and unresolved dependencies produce errors. Editing a definition recomputes downstream results. A live answer tracks selected typed text only while that text remains its expression; entering a different problem creates an independent calculation.

Live handwriting watches a bounded source region after a 700 ms pen-idle delay. Manual expression/definition editing detaches that region. Live scans process up to 32 results with fair rotation. Explicit `y=f(x)` graphs use adaptive real sampling on a CPU worker and persist their range and page variables. Graph display follows the current paper and theme while preserving source SVG geometry and export colors.

In **Check work**, type a next equation or choose **Use handwritten step**, then **Check next step**. Equation comparisons check solution sets, including lost roots; expression comparisons retain domain restrictions and can be conditional. Unsupported comparisons return unknown rather than treating numerical samples as proofs. Word problems use supported deterministic templates and require review followed by **Solve this equation**.

### Engine, setup and limits

`crates/app/src/math_solver.rs` controls a bounded JSON-lines Python service with pinned SymPy 1.14.0 and mpmath 1.3.0. A restricted parser retains source spans and domain restrictions. The service uses no Torch or additional neural model, blocks Internet sockets and caches repeated requests. Opening the panel or solving reviewed recognition prestarts it, overlapping Python/SymPy startup (about 0.3 s) with OCR or review. The process stays resident across panels, setting changes and solver input errors and stops after five minutes without requests. Cancellation kills only a running request; timeouts and protocol failures restart the process. Graph results are rasterized by the panel only. `cargo test -p folio-app benchmark_panel_solve_latency -- --ignored --nocapture` reports panel-to-report latency for representative problems with `FOLIO_MATH_CONFIG` set. The configured computation limit defaults to 8 seconds where supported; the Rust response deadline is 15 seconds. Platforms with Python's `resource` module also enforce a 768 MiB virtual-memory limit. LaTeX parsing and vector-outline conversion run outside the UI thread.

For a development pack, install `scripts/math-solver-requirements.txt` in the chosen Python runtime, then run `python3 scripts/setup-math-solver.py`. Lookup order is `FOLIO_MATH_CONFIG`, `<data-dir>/math-solver/pack.json`, bundled resources, then `artifacts/math-solver/pack.json` for debug builds. The pack retains dependency notices; update Python paths if moving a separately prepared pack. OCR uses its own recognition pack and settings.

Copy/paste and duplication remap math sources; pasting a calculation without its handwriting source detaches the watched region. Current document/database compatibility is described under [Persistence and recovery](#persistence-and-recovery).

Supported arithmetic, algebra, systems, inequalities, derivatives and integration expose steps where available; advanced results may have labeled summaries or explicit errors. There is no symbol-to-stroke alignment, per-subexpression highlighting, implicit/3D graphing, arbitrary word-problem reasoning, general proof checking or universal teaching trace. Handwriting and image recognition require review. Controller routing tests isolate integration from OCR accuracy; synthetic GUI checks do not establish physical input reliability.

## Explicit offline recognition, copy and replacement

Text and math recognition use built-in, pure-Rust stroke-sequence models (`crates/recognition`, `folio-recognition`) bundled directly inside `recognition/` (~38 MiB total, zero downloads, zero external inference servers, and zero Vulkan/GPU dependencies):

- **Math v2 (`recognition/math_v2.frec`, ~19.2 MiB)**: 18.58M-parameter 6-layer RoPE Conformer Encoder + 4-layer KV-cached autoregressive Decoder trained on Google MathWriting with 10 kinematic/spatial stroke features and stroke-order shuffling augmentation. Per-channel INT8 symmetric quantization runs directly from memory-mapped `.frec` files with runtime-dispatched AVX2+FMA kernels on x86_64 (`28.3 ms` median on CPU; `62.5%` EM / `6.83%` CER on the 200-sample MathWriting head-to-head).
- **Handwriting v2 (`recognition/htr_v2.frec`, ~17.1 MiB + `recognition/htr_lm.json.gz`, ~1.6 MiB)**: 16.63M-parameter 8-layer RoPE Conformer-CTC model with two-pass scale-invariant multi-line vector clustering, delayed-stroke reordering (`i`-dots and `t`-crosses), and temperature-calibrated CTC prefix beam search with an English unigram/bigram + character 4-gram lexicon (`56.8 ms` median on CPU; `2.25%` CER / `85.5%` exact line match on the 200-sample unseen-writer benchmark).

### Recognition lifecycle and privacy

All ink stays local and is processed directly as raw vector strokes without rasterization or network access. Raster image and PDF crop OCR are not used. Hovering a recognition control preloads the bundled memory-mapped models and lexicon on the background worker thread; warm requests reuse the resident `Engine`, and five minutes of inactivity unloads the models to release RAM. A bounded session cache reuses results for unchanged sources, pack configuration, and recognition kind (retaining weak source identities, at most eight results, 512 source references, and 256 KiB of result text). Cancel/Esc invalidates pending results immediately.

Live handwriting updates keep the 700 ms writing pause and schedule directly at its deadline, independently of the 600 ms scan used for other linked-math maintenance. Edits, undo and redo refresh the deadline; active interactions defer it. UI maintenance sleeps until the earlier of its normal poll and the pending deadline.

Recognition runs the bundled pure-Rust stroke models on a worker thread. On a recent laptop CPU a warm request takes about 26 ms for a short equation and 46 ms for two handwritten words; the first text request also loads the handwriting model (about 0.3 s).

Pack lookup checks `FOLIO_RECOGNITION_CONFIG`, `<data-dir>/recognition/pack.json`, the bundled `recognition/pack.json` beside the executable (`../recognition/pack.json` or `./recognition/pack.json`), and the workspace checkout during development. External Python mock packs remain supported for deterministic controller tests. Review recognized content before insertion.

Results open an editable review. Copy leaves the document intact. Replace writing removes only captured strokes and inserts editable text or a rendered equation in one journaled command. Math validates and renders before changing the page; failure restores the corrected review and retains the ink. Note/page/source identity is checked before accepting and replacing, and generations reject cancelled responses. Original sensor data stays in durable undo history.

Digit-only handwriting lines use the captured stroke layout to remove false spaces inside compact numbers, for example `1 2 3 4` → `1234`. Correction requires one separable ink group per recognized digit on a shared line. Unequal heights and uneven baselines are accepted when the common vertical band covers at least half the shortest digit and every digit is at least 40% of the line height; tiny ambiguous marks are excluded. Gaps no larger than 35% of the line height are joined. Wide gaps remain separators. Ambiguous or overlapping glyphs, mixed text/formulas, tabs, and line breaks retain the model's spacing. This applies to text and math suggestions before review; user edits are retained as entered.

Keeping ink and indexing the reviewed text makes handwriting searchable without replacing its strokes. Editing or deleting a source invalidates its reviewed index; undo restores it. There is no automatic text detector.

## Glass surfaces and motion

Menus, dialogs, sidebars, the top bar and the footer are translucent over a blurred backdrop. **Settings → Appearance → Glass opacity** (30–100%) and **Glass blur** (0–40 px; Off disables blurring) control them. In the editor the page is painted across the whole window, beneath the bars and sidebars, while input, layout and the viewport stay relative to the visible canvas area. The top bar and the editor footer are most opaque along the window edge and fade to the glass opacity. Hover and selection highlights on glass are a translucent wash of the text color. Settings cards stay nearly solid for readability. Dialog backdrops are dimmed and lightly blurred.

With GPUI, the vendored framework added `Styled::backdrop_blur`; Rune provides `El::backdrop_blur` itself. The Blade (Linux) and Direct3D 11 (Windows) renderers copy the region behind the element from the frame, reduce it by 2–8× depending on the radius, apply a separable Gaussian and composite it inside the element's rounded bounds; the swap chain is therefore created with copy usage. Box shadows are no longer drawn beneath the element that casts them, so translucent surfaces do not show their own shadow. Blur passes run only for frames containing blurred elements. The Windows HLSL is compiled by `fxc` during Windows builds only; the Linux host type-checks the Windows Rust code but not the shaders.

Mouse-wheel scrolling eases over roughly 150 ms in scrollable panels (GPUI) and on the canvas, including Ctrl+wheel zoom; the zoom buttons, Ctrl +/− and Fit ease the same way (Fit only on unrotated pages). Off macOS Rune delivers Ctrl+wheel over the canvas as a magnify without phases; magnifies outside a touchpad pinch (`Began`…`Ended`) ease too and zoom opposite to Rune's mapping. Zoom stays within 25–800% (`Viewport::MIN_ZOOM`/`MAX_ZOOM`); eased zoom aims no further, so scrolling on against a limit builds no backlog. Eased scrolling and zooming head for a target view that each notch changes exactly where it happened, and each frame moves toward it as a zoom about the fixed point the two views share, so a fast run of notches lands where each aimed even when the pointer moves between them; any other change to the view cancels the motion. Zooming keeps the point under the pointer still even where that puts a page stack beyond its scroll limits (the pages no longer slide toward the top when zoomed out); scrolling from there moves back toward the limits without a jump and never further out (`PageStack::clamp_vertical_from`). Touchpad (pixel) deltas and pinches still follow the fingers directly. Menus and popovers grow out of a point at what opened them (the middle of their button, or the clicked point for context menus; `Div::grows_from`) into their full shape without fading, on a one-shot Rune sequence (`transitions::MORPH`, since presence transitions cannot start below half size; each opening gets a new key so it replays), and close by shrinking back into it: each opening sits in a holder (`Transitions::overlay`) that stays mounted after the menu closes (`Transitions::closed`, which call sites emit while the menu is shut) and scales to zero about that point, carrying the leaving menu with it; the tool wheel grows from its centre, the selection toolbar pops up from the selection, dialogs rise and settle while their scrim fades, and the page and solver sidebars slide in, the page gliding to its new centre beside them over 0.45 s on an ease in and out (`CanvasGlide`; the page sidebar also moves the canvas's left edge, which the page first stays clear of on screen, so it never jumps; a resizing window's fine steps follow at once); each leaves by reversing its entrance. Overlays are Rune presence transitions (`transitions::overlay_transition`) in layers that stay mounted while closed (`overlay_layer`, the canvas menu's and the tool wheel's layers), so exits play; exits receive no input and never delay state changes. Most modal dialogs (naming, folders, the document picker, recognition review, pickers) and Help are popovers rather than dialogs: they open under the control that was clicked (above it when there is more room there; near the top when opened by keyboard, `NotesView::popover_frame`), grow from it and shrink back into it like menus, carry no close button, Cancel or key hints, and close on a press outside or Escape. They read as menus: an icon and title row, menu rows for their actions (the confirming one last, with a check), compact fields. The document picker (Ctrl+T) is a command palette: its filter is the header, the matching documents (one line each, the chosen one marked ↵) sit beside a preview of the chosen document's cover page with its folder, page count and edit time, and a footer strip shows the keys beside New document. It grows from and shrinks into what opened it, as the other menus do. The pointer chooses the row it is over, as ↑/↓ do. While it is open the editor keeps library previews instead of releasing them each frame (`release_hidden_resources`). One chosen from a menu (a tab's, card's or folder's context menu, the editor's document actions and pen menus, the Insert and ink-colour dropdowns, and the selection's menu on the canvas, which turns into a recognition's review) does not open a second popover: the menu springs to the dialog's size and its items slide away for the dialog's page (`NotesView::modal_in_menu`, `MenuHost`), whose first row (‹ title) returns to the menu, as Escape does; a press outside closes both, and submitting closes the menu. Settings and confirmations (permanent deletion, unsaved changes, PDF passwords) stay dialogs. Their glass box is frosted at the glass opacity over four times the menu blur (the scrim keeps its soft blur), and while one is open the window's bars and sidebars draw no blur of their own (`NotesView::chrome_theme`): Rune blurs only the first four glass surfaces in a frame (`rune::MAX_BACKDROP_BLURS`), and in the editor the bars used them up, leaving the scrim and the dialog only their tint. Over the library the document picker asks for covers at the size the shelf's cards use (`library_cover_height`), since a page has one cached thumbnail and two sizes would discard each other every frame. These sit in layers that stay mounted (`Transitions::dialog_overlay`): the scrim and the glass box each fade themselves, because a backdrop blur inside a fading ancestor only sees that ancestor's drawing and would pop in when the fade ended. Dialog boxes rise and settle on their own transition, keyed by dialog, so replacing one dialog with another swaps only the box. In the library the search bar filters the shelf by document title as you type (every word must appear; no full-text search, match list or stepping; the commit animates, so cards that no longer match leave and the rest glide to their places), and switching views closes it. The search button (in the library header, and beside the favorite star in the editor) widens leftward in place into the search bar (its box springs edge by edge while its group springs with it, so the buttons after it stay put; 20 rem in the library, 16 rem in the editor) and narrows back into the button. A held control's highlight dims below its hover tint (`Theme::press_wash`) and fades back up as the control springs back; a control that opened a menu keeps its hover tint so it fades instead of vanishing. Switches show no box when hovered; their track lights up. The selection's actions on the canvas are a small menu: Cut, Copy and Delete side by side on top, then Solve, Convert to text and Convert to math (and the actions for equations and images) as rows. The menu is as wide as its rows, and as it turns into a review and back its place springs with its size (`Transitions::selection_glides`, for half a second), where it otherwise follows the selection at once. Recognition reviews show the text a little larger in a field that grows from one line. Text uses Rune's `FontSmoothing::Windfoil` on every platform (CoreText's glyph weight), since the default off macOS drew small text, dark on light most of all, thin and ragged. A loop that selects something (an encircling pen stroke held at its end, or a lasso) morphs into the selection's box over 0.26 s on a sharp ease-out (quintic), each point moving to the place as far along the box's outline as it was along the loop, in the loop's own direction, taking on the selection colour and outline width, then fades over 0.2 s (`Controller::select_morph`, `painting::morph_to_box`). The tour of smart ink (`onboarding.rs`) opens once on first launch (`Settings::tour_seen`) and from Help › Take the tour or Settings › Writing › Take the tour. It fills the window, title bar included (its top bar moves the window and carries Skip and the window controls, which the tab strip then leaves out). One column, centred in the window (as far up from the foot as the top bar comes down), holds the step count, a looping clip of the real app doing the step (welcome, circle to select, scratch out, hold for shapes, auto math, convert, solve, find; a drop shadow lifts it off a light window), its title, two lines kept for its words and the buttons, with the steps named along the foot (each jumps there; the current one is underlined). The rows keep fixed heights, so nothing below the words moves. The buttons have set widths and places about the middle of their row (`buttons_at`), so the tour draws their morph itself on the step's clock: Show me starts alone in the middle; pressing it, it glides aside and resizes as Next on an ease-out-expo while Back fades and grows in beside it and their words cross-fade, and from then on the pair keeps its place (the last step's two buttons widen and change their words in place). ← and → step, Escape or Skip closes, and the last step opens the starter document or a blank page. Its motion runs on two clocks (since it opened, since the step began), set every frame so it lands at once: the title rises word by word out of a blur on an ease-out-expo, the words follow, the clip slides in from the side the tour moved to out of a blur and a slight scale and then floats a few points, the count rises, and on opening the top bar drops in and the step names pop in one after another. Behind it is a grid of faint dots, 14 pt apart, that behave like water (`Ripples`): a damped wave equation on the grid (a nine-point Laplacian, so rings stay round) stepped 110 times a second. It is viscous: besides a slow wave speed and plain damping, each dot's speed is pulled toward its neighbours' (`RIPPLE_VISCOSITY`), which smooths fine ripples away fastest, so wakes and splashes roll out as broad, soft swells and settle quickly. Two slow, broad waves cross the grid all the while, brightening and swelling the dots very slightly, so even still water breathes. The clip and the buttons stand in it as walls (their laid-out bounds, corners included), held still like the window's edges, so waves come back off them and no dots show under them. The pointer drags a thin, quickly damped wake through it as far as it moves, a press on the backdrop drops a round splash, and a button that moves the tour (or the one its key stands for) sends out a wave in its own outline. Each dot brightens and grows with the wave front over it and fades toward the window's edges. All the dots are one Rune shape of round points redrawn each frame (a GPU instance each); still water skips stepping. Reduce Motion keeps the water still and the words in place. Each clip rises out of the paper's colour and sinks back into it, so its loop never cuts (`--reframe` reruns only the camera and encoding on frames already captured). An empty folder shows only a bare folder icon and "Empty folder". Tooltips follow the theme: the popover's colour with a hairline edge and medium-weight text. ## Rendering and persistence performance

The library shelf is a virtual list (`compat::virtual_list`): it scrolls itself and builds only the rows within a viewport of the visible ones, with spacers keeping the scroll extent (row height is measured from the scroll extent, so the interface scale needs no care); scrolling past the built rows builds the view again, and rows built that way appear without their entrance. With 400 documents a frame went from about 43 ms to under 6 ms (the view, about 18 ms, built every card). The canvas builds the view again as soon as it is laid out at a new size, since it paints only once it knows its size. `FOLIO_PROFILE_STARTUP=1` also marks `note_loaded` (the first frame showing the opened document) and `ink_ready` (all of its visible ink as images). A window Rune considers covered redraws only every 250 ms, so measure memory and timing in a visible window, for example `gamescope --backend headless -W 1440 -H 1000 -- folio …`, not one hidden behind others or in `kwin_wayland --virtual`.

UI maintenance polls every 250 ms while idle. Native accessibility actions wake the UI through an asynchronous channel. Input, new animations and background requests made during rendering or virtual-row layout resume 16 ms polling, which continues during active interactions, animations, background work and update checks. Pending save receipts retain fast polling; failed saves and recognition awaiting a download choice do not keep an otherwise idle editor at frame rate. Dropping the view cancels its polling task.

Window-control glyphs use cached SVG alpha masks with their original optical geometry, so a few title-bar lines do not trigger full-window path antialiasing. The Linux Blade renderer allocates its path/resolve and multisample textures only when a scene contains vector paths. Resizing a library-only window does not allocate those targets. Existing targets retain resize hysteresis; replacements wait for GPU completion and are created only if a later scene needs them. Drawing keeps its configured antialiasing sample count. During an interactive Wayland resize the swapchain also keeps up to two 64-pixel steps of spare capacity, cropped off with `wp_viewport`, because recreating it cost about 1.3 ms per step on an AMD iGPU and 8 ms on an NVIDIA dGPU; it returns to the exact size when the resize ends. On multi-GPU Linux machines Folio renders on the firmware's display GPU unless `ZED_DEVICE_ID`, `DRI_PRIME` or `MESA_VK_DEVICE_SELECT` selects another. On the Rune branch, startup also limits the Vulkan loader (`VK_LOADER_DRIVERS_SELECT`) to that GPU's driver plus lavapipe unless a driver or GPU variable is already set; enumerating adapters otherwise loads every installed driver (NVIDIA's added about 60 MiB RSS and may wake the discrete GPU). Library chrome (title bar, sidebar) is not blurred, since nothing passes behind it and each blurred surface reserved tens of megabytes of GPU memory. A `RenderImage` holds either its premultiplied pixmap or its Rune pixels and releases the pixmap once the pixels are made, since Rune keeps its own copies. Targets already used by an editor remain warm until resize or window destruction; returning to the library does not reset every renderer/font cache. Compare base RAM before opening any editor in release builds: debug code pages and software-driver allocations can account for much of the apparent startup footprint.

Finite-page stack layout is shared by painting and navigation and rebuilt only for page structure or dimension changes. Autosave and accessibility share command-aware searchable-text snapshots; geometry-only edits reuse them while text, reviewed-handwriting and source-visibility changes invalidate them. Text hit testing visits spatial candidates in drawing order. Bulk spatial edits rebuild dense buckets once and retain measured bounds for unchanged text. Multi-page command application indexes page identities lazily and resets that lookup after structural changes; autosave deltas cache page lookups and index only after repeated scans justify it. Ordinary incremental saves reconcile touched pages; structural/full snapshots reconcile the complete page identity set. Page duplication avoids copying maps and drawing order that it immediately replaces.

Library startup defers loading editor documents and their undo journals until a document is opened. Loading shares identical immutable raw/path buffers across current ink, erased fragments and undo snapshots, comparing every sensor bit; the persisted format and complete undo history remain intact. Closing a durable tab releases its session and object previews, including the last editor tab. A bounded view-state cache remembers page, zoom, pan and rotation for up to 128 released notes during the same app run, independently of the restart preference. Unsaved edits, failed saves, deferred actions, background imports and equation renders retain their sessions until safe. Inactive sessions use an estimated 96 MiB model budget and an eight-session limit; the active session remains resident. Cover page models retain up to 48 recent entries. Estimates count shared ink buffers once and are cached until the session changes. Loading an editor removes its separate cover model. Ink-only previews, batches and PNG exports avoid initializing the export font database; text and embedded SVGs retain font support.

The folder sidebar renders visible rows, with collapsed descendants excluded before layout. Editor accessibility updates bypass folder indexing when no folder labels are requested. Hierarchy order and identity lookups are shared, and path labels are resolved on demand with a 16 MiB retained-text budget. Accessibility removes offscreen probe rows after scrolling. Folder arrow navigation uses the complete expanded tree and scrolls/focuses offscreen destinations, including wraparound. Long text fields paint visible rows and reuse shaped-line width and binary caret lookup. Native glyph/emoji painting rejects clipped raster bounds before populating the GPU atlas. Export and solver graph previews release replaced/closed GPU images. Atlas textures retire after their last submitted GPU frame, and abandoned uploads are removed before texture identities are reused. Freed image tiles return their atlas allocation on Linux and Windows even when neighboring images remain resident. Recovery awaits its background task without idle polling, successful settings/folder writes leave the retry queue immediately, and offline subprocess deadlines include blocked input writes while output pipes continue draining beyond the retained diagnostic limit. Each offline call owns a Unix process group or nested Windows job; normal worker descendants inherit this ownership and are terminated before pipe threads are joined. Windows workers join their cleanup jobs before executing, so fast launchers cannot spawn helpers or exit before ownership is established.

Ordinary edits update only changed spatial-index entries and the source references of derived shapes/equations. Reference counts keep an original stroke hidden when several derived objects share it, including after undo/redo. Command application no longer scans every page to restore drawing order; appended ink keeps its existing order, while insertion/deletion restoration remains exact. Batch deletion filters each affected page's drawing order once, and undo merges distinct insertion positions without shifting the remaining objects repeatedly. Mixed delete/insert commands defer unrelated removals until the end of the command, avoiding repeated order scans when replacing strokes with fragments. Reusing an object identity removes its old order entry immediately. Page replacements preserve their sequence; equal insertion positions retain stable insertion behavior. Session drawing-order ranks update incrementally for appended objects and are rebuilt for removals or middle insertions. Sparse copy, edit, recognition and math-panel actions use those ranks to visit only selected objects and any required source strokes; dense selections follow page order without sorting. Recognition eligibility reuses indexed hidden-source counts instead of scanning unrelated objects. Small object transforms that stay in the same grid cells update exact bounds without replacing cell memberships. Dense spatial queries choose a bounds scan before hashing repeated cell references; sparse indexes retain one grid pass.

The renderer caches the ordered visible object set with a small margin equivalent to 64 logical pixels at the current zoom. Small resize and pan steps reuse both that set and its ink batch plan; leaving the cached area, changing content/index bounds or substantially shrinking the viewport rebuilds it. Canvas transforms and clipping still follow each frame's exact bounds, preserving ink scale and revealing newly exposed content. Dense visible sets follow page order directly; sparse sets sort only visible candidates by their cached ranks. Completed path-cache maintenance runs when that set changes rather than on every pen frame. Unrotated paper and its shadow use GPU rectangles; ruled and grid backgrounds cache thin rectangles per viewport/theme/display density. Fractional device-pixel edges use weighted coverage to preserve line thickness during resizing and on scaled displays. Rotated pages and dotted backgrounds retain compound paths, removing paper's full-viewport path-rendering pass from ordinary blank, ruled, grid and PDF pages. Background spacing doubles as needed to keep marks at least 16 logical pixels apart when zooming out, bounding infinite-canvas geometry by screen area; retained dots stay on the original document lattice. Dots use direct convex triangle fans instead of tessellating disconnected contours together. `cargo test -p folio-ui benchmark_infinite_paper_zoom_out -- --ignored --nocapture` compares CPU path tessellation and rectangle preparation during pan at several zoom levels, not GPU frame time. Object previews share their immutable BGRA buffer with the GPU image wrapper instead of retaining a second CPU copy. Theme adaptation allocates only when a pixel color actually changes; recolored graphs retain their separate rendering. These conversions run on GPUI background tasks, with at most two in flight. GPU uploads still require their own device storage. Rendering rejects stale source objects, pixels and theme results. The controller trims preview/session caches every 250 ms instead of scanning them every UI tick. Worker results are bounded to eight items rather than 64, limiting queued decoded-image accumulation; this is not a bound on total application RAM.

The thumbnail cache holds up to 48 entries and renders at most two replacements concurrently. Infinite-canvas thumbnails in the page sidebar and library show a page-shaped crop of the opening content, bounded to one paper size so distant notes do not shrink the preview; exports and export previews still include the full content. Eviction and content/theme invalidation remove old images from the GPU sprite atlas as well as the Rust cache. Object-raster replacement, offscreen eviction and page eviction release their atlas images too. PDF prefetch keeps visible pages and a small neighboring working set; distant decoded assets and their uploaded images are released together. Opening the library releases editor page geometry, ink/object images and decoded PDFs. Reopening the editor rebuilds its visible canvas caches. The editor keeps the library's cover thumbnails (within the cache limit) so the shelf shows them at once on return, and drops other thumbnails while the page sidebar is closed.

The renderer caches settled ink on Linux and Windows as images of fixed 32-object blocks of the page order, split at other objects and at selected or erased ink. A batch includes its offscreen members, so panning and zooming never change batch membership. Up to half the available cores (two to six) rasterize per page; cached images are limited to 16 million pixels per visible page and one million pixels per batch, and oversized batches use vectors. During a zoom, cached images are scaled on the GPU and rasterized again at the new device density once the zoom rests for 140 ms (or immediately past a 2× change); the previous image stays on screen until its replacement is ready, and up to half the pixel budget of offscreen images is kept for zooming back out. The pages above and below the viewport prepare their images ahead of scrolling. While the view moves, ink without an image is tessellated within a 6 ms budget per page and frame; the rest follows over the next frames. Ink that is only in the retained margin, not on screen, waits for its image instead of being tessellated. Selection, erasing, object changes and themes invalidate affected batches immediately; stale jobs cannot replace current ink. Dropped pages/images release their atlas entries. Live ink and exports remain vector-based. The isolated `cargo run --release -p folio-ui --example ink_layers` fixture exercises default caching, selection, theme and zoom invalidation, including 60 window grow/shrink steps, rotated infinite dotted paper down to 10% zoom and canvas cache release/rebuild when visiting the library, without opening installed update caches. It defaults to 1,024 strokes; `FOLIO_INK_FIXTURE_STROKES=4096` exercises a denser page. `cargo test --release -p folio-ui benchmark_dense_saved_ink_scene_preparation -- --ignored --nocapture` measures CPU scene geometry and resize culling/batch preparation, not GPU frame time or physical input latency.

The Linux Blade backend uses a frame upload pool for path geometry and image staging. Buffer capacities grow geometrically; completed smaller buffers are released when replaced, and unused buffers retire after a short reuse window. GPU completion gates both reuse and retirement. Dense writing therefore does not retain every preceding upload size, and leaving a large scene releases its unused upload capacity. Device-free pool regressions cover growing scenes, shrinking working sets, alignment and in-flight buffers. Native dense-page smoke checks use software Vulkan on a private X11 display; they do not establish physical pen latency or guarantee recovery from an unrelated GPU-driver failure.

Scratch erase accepts sustained advancing up/down scrubs across existing writing, without requiring horizontal return passes. It still requires broad reversals with deliberate turnarounds, rejects smooth waves and ordinary W/M handwriting, targets actual ink crossings and remains one undoable operation.

Preview completions/errors for edited, deleted or evicted objects are discarded. Edits, undo and redo release obsolete cached pixels and failed-preview source references immediately; ordinary object edits check only their own cache keys. Pure moves instead shift the existing preview onto the moved object. After a resize, stretch or rotation, the canvas keeps drawing the previous raster carried by the edit's transform until the fresh raster is uploaded, so releasing a drag never hides an image or equation. Page replacement and deletion release stale previews on the affected pages while preserving unchanged sources. Cover changes release old session snapshots before another library request, and editing a loaded note discards its separate library preview. Offscreen-page results cannot insert their bounds into the active page's index. Higher-resolution previews are retained when a smaller render budget would already suffice. Repeated document-load requests are coalesced, and a failed queue submission no longer leaves a tab indefinitely pending. A failed held-pen shape fit runs once until the pen moves substantially, preventing repeated stationary fitting; endpoint tremor tolerance and continued drawing/shape recognition remain intact. Saturated grid-cell counts use checked arithmetic; extreme imported coordinates and non-finite query bounds cannot overflow the index or cause huge grid allocation.

CPU benchmarks measure command application and spatial-index maintenance separately from drawing, persistence and presentation; their reductions must not be read as equivalent improvements in physical pen latency. Full-document save/load still scale with document size.

## Architecture

The workspace separates `apps/desktop` and `app`, `ui`, `input`, `ink`, `canvas`, `document`, `storage`, `gestures`, `shapes`, `math`, `pdf`, `search`, `export`, and `platform` crates. Rust 1.92+ is required by the subset-font PDF backend. Ink, geometry and structured documents have no GPUI dependency. The UI forwards operations to a controller; document mutation and LaTeX rendering are outside the presentation layer. Explicit optional recognition lives in `app::recognition`, with a resident native Q8 backend and support for existing Python packs; no automatic text detector is present.

Inside `crates/app`, `Controller` (in `lib.rs`) owns all application state; its methods are grouped by concern in sibling modules (`session`, `history`, `notes`, `interaction`, `selection`, `background`, `import_export`, `previews` and others), listed in the crate documentation. `crates/ui` builds each frame in `frame.rs`, keeps control enablement rules in `controls.rs` and the Document actions menu in `document_actions.rs`. `crates/document` separates geometry, objects, pages, validation and commands into modules re-exported from its root.

With GPUI, native Linux patches provide Wayland tablet-v2 frames, tablet pads and pointer pinch gestures, and XInput2 pressure/tilt. Six pen styles share an incremental pressure/velocity filter and vector outlines. Raw and processed vectors are shared immutable arrays so transformations and undo do not copy sensor buffers. Raw samples survive smoothing, transforms, segment erasing, shape/equation conversion and refinement. Each erased fragment keeps original sensor samples plus an independent visible path.

Completed paths are cached; opaque active ink is divided into 256-point chunks with a bounded mutable tail. Translucent active ink uses one compound fill for consistent overlap opacity. A uniform-grid spatial index updates changed objects and derived-source reference counts and culls offscreen content. Visible objects remain in cached document order across small viewport changes; content/index changes and movement beyond the retained margin refresh the set. Paper geometry is also cached. Images, text and equations use bounded worker-generated previews; GPUI transforms those raster sprites on the GPU, keeping them aligned with vector ink during pan, zoom, resize and rotation.

Message-passing workers separate persistence, document/rendering processing and search/load. Each expensive processing queue holds at most 16 jobs; the result channel holds eight items. GPUI pixel preparation has a separate two-task bound. Search generations coalesce obsolete search jobs. Persistence uses a 64-item channel; saturation or disk errors retain the live document and bounded command history for a full retry rather than blocking pen input or accumulating failed deltas indefinitely.

## Persistence and recovery

SQLite uses WAL, `synchronous=FULL`, foreign keys, stable UUIDs, per-object rows and atomic document/search/journal transactions. Schema version 6 adds an indexed, stable page-to-FTS-row mapping independent of SQLite page rowids, plus note/page-position and draft indexes. Every writer open upgrades older databases transactionally; versions 3–5 retain their existing valid FTS rows, while older databases first rebuild legacy OCR search content. Earlier builds reject schema 6. Search updates use rowid lookups and skip unchanged content. The current document format is 4. Format 3 introduced optional math links alongside the version 2 cut-path and character-group records; earlier document formats remain readable. Editing upgrades the format, and clipboard writes use V2 while accepting V1. Each history holds at most 512 commands; full catch-up saves replace its journal consistently with the current live state.

Normal edits write changed objects and affected page headers/FTS rows. Metadata-only edits update searchable titles/tags without rebuilding every page. Active ink drafts are saved approximately once per second. Completion clears the draft in the stroke transaction. Periodic SQLite snapshots retain three generations. Assets must be backed up with the database.

Recovery never overwrites or renames the original data. It prefers a healthy checkpoint, otherwise salvages independently readable records into a new sibling directory, copies assets, and writes `RECOVERY.json` with issues. Asset maintenance considers current documents, undo history and retained snapshots and moves unused files to `orphaned-assets`; it does not permanently delete them. Damaged snapshots stop maintenance rather than guessing references. Save errors remain visible and retry from the retained live document.

## Dependency and packaging decisions

Rune is pinned to a `dev` revision; the previously vendored GPUI 0.2.2 and its extensions are recorded in [vendor/README.md](vendor/README.md). Geometry algorithms are original implementations informed by perfect-freehand, Xournal++ and Rnote; no algorithm source was copied. Krilla/krilla-svg provide maintained subset-font PDF output, lopdf preserves original objects/decrypts PDFs, Poppler renders only requested background previews, and latex-rust renders equation outlines locally. [LICENSES.md](LICENSES.md) records the locked Rust graph and retained notices.

`scripts/package.py` produces a desktop archive and complete Cargo-vendored corresponding-source archive with notices. Models and Python inference runtimes are excluded. `scripts/package-distros.py` creates RPM and Debian packages without installing them. The launcher prefers native Wayland when available; `FOLIO_FORCE_X11=1` selects X11 for that process only. Folio is single-instance per data directory: a later launch for the same library forwards the launcher's `XDG_ACTIVATION_TOKEN`/`DESKTOP_STARTUP_ID` to the lock owner over a socket in `$XDG_RUNTIME_DIR` (`app/$FLATPAK_ID` in Flatpak) and exits. The owner activates its window; compositors that refuse focus stealing may show an attention request instead. Fixtures, `--recover` and update restarts always start their own process; startup actions such as `--new-note` or files are not forwarded.

Library initialization runs on a startup worker while the main thread prewarms the GPU (`rune::prewarm_gpu`). The window opens after both finish; integrity checks and workspace restoration complete before editing begins, and library failures still open the recovery window.

For databases of at least 4 MiB, startup reads ahead through at most the first 64 MiB using a reusable 1 MiB buffer before SQLite's whole-database `quick_check`. This reduces small cold reads without skipping validation or changing WAL/FULL durability. Read-ahead is best effort; SQLite still reports storage errors normally. Set `FOLIO_PROFILE_STARTUP=1` when launching to log elapsed milliseconds from entry into `main` through platform setup, library readiness, window construction and the first frame callback. These CPU milestones exclude process loading and compositor/display presentation; measure visible startup in a private desktop for comparisons.

## Validation and measurements

Run `cargo test --locked --workspace -- --test-threads=2`, `cargo fmt --all -- --check`, and `python3 scripts/check-documentation.py`. Workspace tests cover document compatibility, raw-data preservation, ink/gesture geometry, undo/redo/reopen, storage recovery and rollback, search, recognition review, solver cancellation and stale results, and UI cache/field behavior. Native smoke replay and accessibility checks use private desktop sessions and throwaway documents; synthetic checks do not establish physical tablet reliability.

Reproduce CPU measurements with `cargo run --release --locked -p folio-app --example benchmark -- 10000` (also use `50000`). Command application, spatial updates, initial save and load are separate measurements; they exclude GPU presentation, compositor and physical-device latency. `FOLIO_PROFILE_INK=1` reports dispatch-to-CPU-paint timings. `FOLIO_PEN_RECORD=/new/path.jsonl` records rich pen frames asynchronously; a bounded queue drops diagnostics instead of delaying ink. Keep generated evidence under ignored `artifacts/validation/`.

`cargo run --release --locked -p folio-app --example benchmark_controller -- 10000` (also use `50000`) measures loaded library covers, single-object copy/move, recognition eligibility, opening the math panel for selected text, deferred edits, and deletion/replacement/undo of alternating objects. Deletion, replacement and restoration time document command application only; they exclude controller indexing, persistence and drawing. Math-panel timing excludes solving, OCR and rendering. The fixture checks that repeated restoration preserves objects and drawing order.

The controller benchmark also measures mouse text hits in ink-heavy pages. `cargo run --release --locked -p folio-app --example benchmark_background -- 10000` measures database opens, variable lookup, continuous navigation through 10,000 finite pages, autosave-delta construction for 512 changed objects on the last page, and a small edit/save on the first two pages. `cargo run --release --locked -p folio-canvas --example performance` includes dense-cell deletion/undo alongside geometry kernels. These are CPU measurements on generated fixtures; use the same machine and build profile for comparisons.

For RAM comparisons, use matching build profiles, a private desktop and copies of the same fixture. On Linux, record RSS/PSS from `/proc/<pid>/smaps_rollup` at library startup, after the editor finishes loading, after durable undo/redo, and after closing the tab. Include blank and history-heavy notes. Wait for asynchronous loads and saves before sampling; a loading overlay is not a settled editor. Software Vulkan places driver/image allocations in system RAM, so its absolute footprint does not predict hardware-GPU usage. Released model allocations may remain in the process allocator; validate ownership release as well as RSS.

## Remaining validation and technical limits

- A physical Intuos BT S was used for incident and OS transport/policy testing. Folio's physical pen rendering and measured 120 Hz hardware-to-display latency remain unverified. Palm rejection, HiDPI tablet calibration, pad layouts and hardware button mappings need further device trials. The app suppresses pointer emulation during pen proximity; the compositor remains responsible for rejecting native touchscreen palm contacts.
- Native work is verified on this Fedora GNOME Wayland/Xwayland session, with builds/tests also run in Debian bookworm. COSMIC, KDE, other distributions, screen-reader workflows and HiDPI sessions require their own runs. Packaging and AT-SPI interfaces do not substitute for certification.
- Original PDF objects are preserved, but digital signatures become invalid when an annotation export changes the document. Complex multi-source named destinations, conflicting form resource/name dictionaries and unusual PDFs need broader corpus testing. The original retained files remain intact. Preview resolution is bounded; vector originals are retained for PDF export.
- Pixel previews use a 128 MiB controller cache and adapt to the visible working set. Model budgets are eviction targets, not a cap on application RAM: active/unsaved documents, allocator retention, fonts, GPU/GPUI images and visible geometry have additional costs. Extremely large visible geometry still requires GPU profiling. Dirty note sessions are retained instead of evicted when saves fail or autosave is disabled.

Priorities are physical pen trials, larger ink workloads and PDF corpus evaluation, then cross-desktop/distribution and assistive-technology certification. No account, network service, proprietary SDK or sync backend is required.
